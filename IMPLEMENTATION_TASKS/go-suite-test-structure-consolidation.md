# Task: Goテスト群の必要性・重複と並列化の再評価

## Original instruction

2026-10-17 ユーザー原文:

```text
### 3. テスト群の構造的整理を追加する

現在のGo suite高速化は、テストを並列化する前に、テスト群そのものの必要性と重複を十分に評価すべきだったと考えています。

既存のRegression Testを、不具合ごとに永久保存することを品質要件としないでください。

重要なのは現行の契約と、独立した故障モードについて必要十分な再発防止能力を維持することです。

同じ不変条件を繰り返し検証するテスト、別のテストに包含されたテスト、現行仕様では不要になった古いテストについて、統合・簡素化・削除を評価してください。

ただし、テスト件数や実行時間を削減するためだけに、独立した重要な検証能力を失わせることは禁止します。

これは既存の並列化を無条件に全て維持するという意味でも、逆に全て破棄するという意味でもありません。重複削減と並列化を、保守性・検証能力・実行時間から再評価してください。

### 4. 独立Taskと実施順序

テスト群の構造的整理は、現在の高速化Taskとは分離できる責務なので、既存Taskとの重複を確認したうえで独立Taskとして登録してください。

ただし、その独立Taskを単純に現在の高速化Taskの最後へ追加して済ませないでください。本来は高速化の実装前に評価すべき内容です。

まず、既存成果・Runtimeを保全したまま、正規Lifecycleの範囲で独立Taskへ切り替えて先行実施できるか評価してください。

可能ならテスト構造整理を優先し、その結果を踏まえて高速化Taskの成果を最終採用してください。

切替が正規に成立しない場合は無理に操作せず、現ACTIVEの中で少なくとも既存テストの重複・必要性・過剰な並列化を評価し、必要な整理を実施してください。独立Taskは最優先の後続Taskとして配置してください。

現在の成果と未完了要求を失わず、同じ調査・実装を二重に実施しないようにしてください。
```

## Purpose

現行契約と独立故障モードの検出能力を維持し、テスト構造と並列化を保守性・実行コストから整理する。

## External feasibility

status: not-applicable

## Contract

- 既存証拠・Gitと分離元の評価を優先し、契約・故障モード・観測結果・重複/包含関係・共有資源・Fixture/Gitコストを対応させて採否を判断する。
- KEEP / CONSOLIDATE / SIMPLIFY / REMOVEと並列/逐次の選択を、検証能力と実行コストの根拠で説明する。不具合単位の永久保存や件数削減を目的にしない。
- 同じ不変条件の反復、他のテストに包含された保証、現行仕様で不要なケースを統合・簡素化・削除し、独立した重要な負例・故障モードを維持する。
- 現在の並列化を全維持・全撤回とせず、process/global/環境/外部ツール共有の境界と実測を根拠に選ぶ。
- 分離元で整理したrunner liveness境界、corpus出版Fixtureの共通初期化、process/global共有の並列実行境界は、Gitと既存artifactを引継ぎ元とし、同じ調査・実装を繰り返さない。本Taskの残余責務は、それら以外のsuite全体の契約・故障モードに対する重複/包含・古いシナリオ・過重な統合確認の横断整理とする。必要な整理を分離元から先送りする根拠にせず、後続実行の前に既存成果との重複と残余責務を再確認する。

## Must not

- テスト件数や時間だけを理由に検証能力を失わせない。skipや緩い期待値で成功を作らない。
- 別TaskのGuard再設計や新しい検出framework、旧仕様維持だけの互換テストを追加しない。
- 分離元で済んだ調査・実装を二重に実施しない。
- GLMにGit remote writeやparent-managed metadata編集を許可しない。

## Acceptance criteria

- 採否ごとに現行契約と独立故障モード、残る検証ownerを示し、削除・統合による保証の欠落がないことを確認する。
- 対応する局所・回帰検証で不正挙動を検出し、有効な挙動を通す。
- 実行時間、処理単価、並列競合、保守負担を区別して評価し、未測定を実績扱いしない。
- 独立Reviewと正規Lifecycleで完了し、今回限りの復旧・通し省略特例は別途許可なく継承しない。

## Historical invariants

- 品質はテスト本数ではなく、現行契約と独立した重要な故障モードの検出能力で評価する。
- Source・Task・証拠の帰属と正規Lifecycleを維持する。
